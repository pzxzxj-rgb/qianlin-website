# 多租户隔离规范

## 1. 目标

确保 `qianlin-website` 中不同旅行社的数据严格隔离。

任何租户都不能读取、修改、删除、关联、覆盖或推断其他租户的私有数据。

规则优先级：

1. 租户隔离与数据安全
2. 数据完整性
3. 认证与授权
4. 生产环境安全
5. 测试完整性
6. 架构一致性
7. 开发便利性
8. 性能优化

不得为了减少代码、加快开发或通过测试而降低租户隔离要求。

当前项目主要使用：

- Next.js
- Vinext
- React
- TypeScript
- Cloudflare Workers
- Cloudflare D1
- Drizzle ORM

当前正式租户：

```text
qianlin-travel
```

当前演示租户：

```text
yunnan-demo
```

当前管理员后台只允许管理：

```text
qianlin-travel
```

当前尚未建立完整的：

- 用户系统
- 组织成员关系
- RBAC 权限系统
- 多租户管理员账号体系

在完成上述系统之前，不得擅自把当前后台改成通用多租户后台。

不得仅通过修改 Session 中的 `tenantId`，就宣称已经支持多个商家后台。

- 修改公开租户 API

- 修改后台读取或保存数据的 API
- 修改 `lib/admin/` 下的数据访问逻辑
- 修改任何包含 `tenant_id` 或 `tenantId` 的查询
- 增加联系方式管理
- 增加线路管理
- 增加目的地管理
- 增加咨询记录管理
- 增加管理员账号、组织或权限功能
- 增加新的租户业务表
- 修改租户专属文件或图片记录
- 修改批量更新、批量删除或数据导入功能

- 修改 Session 中的租户信息
- 修改租户隔离测试
- 修复任何跨租户安全问题

- 纯 CSS 修改

- README 中与租户逻辑无关的文字修改

如果无法确认某项数据是否属于租户，默认按租户数据处理。

## 4. 可信租户上下文

所有租户查询和写入，都必须使用服务端确认的可信租户上下文。

### 4.1 公开网站

公开网站的租户应来自：

1. URL 路径中的 `tenantSlug`
2. 服务端根据该 slug 查询数据库
3. 服务端确认租户存在且状态符合要求
4. 服务端使用数据库返回的租户 ID 执行业务操作

正确流程：

```text
URL tenantSlug
→ 服务端查询 tenants 表
→ 获得可信 tenant.id
→ 使用可信 tenant.id 查询或写入业务表
```

不得直接相信客户端请求体中的：

- `tenantId`
- `tenant_id`
- `tenantSlug`
- 用于选择租户的其他字段

客户端提交的租户字段不能决定数据写入哪个租户。

### 4.2 管理后台

管理后台的租户必须来自：

- 已验证的 HttpOnly Session
- 服务端验证通过的管理员租户上下文

不得从以下位置直接决定管理员所属租户：

- 表单字段
- JSON 请求体
- URL 查询参数
- localStorage
- sessionStorage
- 未验证的 Cookie
- 未验证的 Header
- 页面隐藏字段

当前后台 Session 只允许对应：

```text
qianlin-travel
```

其他租户 Session 必须被拒绝。

### 4.3 Header

即使未来使用：

```text
X-Tenant-ID
```

也只能把它当作租户选择信息，不能直接当作授权结果。

服务端仍然必须验证：

- 当前用户身份有效
- 当前用户属于目标租户
- 当前用户拥有相应权限
- 目标资源属于同一租户

## 5. 客户端字段处理规则

以下字段属于高风险租户身份字段：

- `tenantId`
- `tenant_id`
- `tenantSlug`

租户写接口原则上应拒绝客户端提交这些字段，而不是静默忽略。

### 5.1 关于 `slug`

不能把所有名为 `slug` 的字段都视为非法字段。

资源自身的 slug，例如：

- 目的地 slug
- 线路 slug
- 文章 slug

可以作为合法业务字段接收，但必须满足：

- 该 slug 只能标识当前租户内的资源
- 不能用于决定租户身份
- 必须经过格式验证
- 必须限制长度
- 必须拒绝路径穿越或特殊危险字符
- 必须在可信租户范围内检查唯一性
- 唯一约束必须包含 `tenant_id`

正确示例：

```text
UNIQUE (tenant_id, slug)
```

错误示例：

```text
UNIQUE (slug)
```

除非业务明确要求全平台唯一，否则不能设置成全平台唯一。

## 6. 数据查询强制规则

所有租户数据查询都必须包含可信租户条件。

正确方向：

```ts
where(
  and(
    eq(table.tenantId, trustedTenantId),
    eq(table.id, resourceId),
  ),
)
```

禁止只通过资源 ID 查询租户资源：

```ts
where(eq(table.id, resourceId))
```

以下操作都必须限制租户：

- SELECT
- INSERT
- UPDATE
- DELETE
- COUNT
- EXISTS
- 搜索
- 分页
- 排序
- 导出
- 后台列表
- 关联查询
- 批量查询
- 批量更新
- 批量删除
- 状态更新
- 图片更新
- 资源排序

不得依赖开发者“记得手动添加 tenant_id”作为唯一安全机制。

应优先使用：

- 统一租户数据访问函数
- 明确要求 `trustedTenantId` 的函数参数
- 服务端租户 Context
- 统一后台租户解析函数

数据访问函数不得在租户参数缺失时默认使用 `qianlin-travel`。

---

## 7. 新增数据规则

新增租户业务数据时：

- `tenant_id` 必须来自可信服务端上下文
- 不得使用客户端提交的 `tenant_id`
- `tenant_id` 必须为 `NOT NULL`
- 应建立指向 `tenants.id` 的外键
- 不得给租户表设置隐藏默认租户
- 不得通过空值自动回退到默认租户
- 关联资源必须重新验证属于当前租户

错误示例：

```ts
tenantId: body.tenantId
```

正确方向：

```ts
tenantId: trustedTenant.id
```

---

## 8. 更新数据规则

更新租户数据时：

- 必须同时使用资源 ID 和可信 `tenant_id`
- 不得允许客户端修改资源所属的 `tenant_id`
- 不得允许通过其他租户资源 ID 修改数据
- 不得先按 ID 查询，再在应用层判断租户
- 应尽量直接在数据库查询条件中限制租户
- 更新失败时不得透露其他租户资源是否存在

正确方向：

```ts
where(
  and(
    eq(resource.id, resourceId),
    eq(resource.tenantId, trustedTenantId),
  ),
)
```

---

## 9. 删除数据规则

删除租户数据时：

- 必须同时验证资源 ID 和可信租户 ID
- 不得只按资源 ID 删除
- 必须检查关联记录是否属于同一租户
- 必须确认级联删除不会跨租户
- 批量删除必须限制在当前租户内
- 混入其他租户资源时，整个操作应失败或安全忽略，具体行为必须明确
- 删除结果不能泄露其他租户资源是否存在

当前项目租户业务表优先使用：

```text
ON DELETE RESTRICT
```

这样可以防止误删租户时连带删除大量业务数据。

---

## 10. 数据库 Schema 规则

所有租户专属业务表原则上必须包含：

```text
tenant_id NOT NULL
```

并建立指向：

```text
tenants.id
```

的外键。

创建或修改租户表时必须检查：

- 是否存在 `tenant_id`
- 是否为 `NOT NULL`
- 是否有外键
- 删除策略是否安全
- 是否有必要的联合索引
- 唯一约束是否为租户内唯一
- 状态字段是否有 CHECK 约束
- Migration 是否兼容已有数据
- 是否可能产生孤立数据
- 是否可能出现空租户 ID
- 是否错误使用默认租户

真正的平台级全局表可以不包含 `tenant_id`，但必须明确说明：

- 为什么它属于全平台
- 为什么所有租户共享不会泄露数据
- 租户是否可以修改
- 是否需要平台管理员权限

---

## 11. 唯一约束规则

租户内唯一的数据必须包含 `tenant_id`。

正确示例：

```text
UNIQUE (tenant_id, slug)
UNIQUE (tenant_id, code)
UNIQUE (tenant_id, external_id)
UNIQUE (tenant_id, email)
```

除非业务明确要求全平台唯一，否则不得只设置：

```text
UNIQUE (slug)
UNIQUE (code)
UNIQUE (email)
```

不同旅行社应当可以拥有相同的：

- 目的地 slug
- 线路编号
- 内部资源名称
- 联系方式标签
- 外部系统编号

---

## 12. 索引规则

索引必须根据真实查询设计。

不得机械地给所有表只增加：

```text
INDEX (tenant_id, created_at)
```

可能的索引形式：

```text
INDEX (tenant_id, status, created_at)
INDEX (tenant_id, status, display_order)
INDEX (tenant_id, slug)
INDEX (tenant_id, available_for_planning, route_order)
```

建立索引前必须检查：

- WHERE 条件
- 排序字段
- 状态过滤
- 是否存在重复索引
- 字段顺序是否匹配查询
- D1 和 SQLite 是否兼容
- 该索引是否真的会被当前查询使用

---

## 13. 关联查询规则

关联两个租户业务表时，必须确认它们属于同一租户。

不得只根据资源 ID 建立跨表关联。

必须检查：

- 两张表是否都属于当前租户
- JOIN 条件是否包含租户边界
- 外键是否可能关联到其他租户
- 客户端提交的关联资源 ID 是否重新验证
- 返回数据是否包含其他租户记录

例如客户端提交：

- 目的地 ID
- 线路 ID
- 图片 ID
- 咨询 ID
- 联系方式 ID

服务端都必须重新在当前租户范围内查询。

---

## 14. 批量操作规则

批量更新、批量删除、排序和导入属于高风险操作。

必须保证：

- 所有目标资源都属于当前租户
- 查询本身限制 `tenant_id`
- 客户端不能通过 ID 列表混入其他租户资源
- 不能只检查第一条资源
- 不能只比较处理数量
- 数据库事务或等效保护能够防止部分写入
- Tenant A 操作后 Tenant B 数据保持不变

批量请求中出现其他租户资源时，必须有明确安全策略：

- 整批拒绝，或
- 只操作当前租户资源并明确返回结果

不得静默产生不可预测的部分成功。

---

## 15. 管理后台规则

当前后台固定服务：

```text
qianlin-travel
```

在建立以下模型前，不得开放其他租户后台：

- users
- tenant_memberships
- roles
- permissions

未来开放第二家旅行社后台前，至少必须完成：

- 用户身份模型
- 用户与租户成员关系
- 租户角色
- 服务端权限验证
- Session 或 Token 租户策略
- 登录后的租户切换策略
- 跨租户越权测试
- 审计日志设计
- 管理员邀请和移除策略

不得只修改前端页面或 Session 字段，就宣称多租户后台已经完成。

---

## 16. API 输入验证

租户写接口必须使用字段白名单。

以下租户身份字段原则上必须拒绝：

- `tenantId`
- `tenant_id`
- `tenantSlug`

以下可能改变资源归属或平台状态的字段也必须谨慎处理：

- `ownerId`
- `siteStatus`
- `isDemo`
- `organizationId`
- `createdBy`
- `tenantRole`

资源自身的 `slug` 可以合法存在，但必须按照本 Skill 第 5.1 节处理。

未知字段应被拒绝，不得默认全部接收。

高风险非法字段应返回明确的：

- 400
- 401
- 403
- 404

具体状态码应遵循当前接口契约。

---

## 17. 错误信息规则

跨租户访问不得泄露：

- 其他租户资源是否存在
- 其他租户名称
- 其他租户资源 ID
- 其他租户联系方式
- 其他租户咨询内容
- 其他租户客户信息
- 其他租户管理员信息

根据接口安全策略可以返回：

- 401：身份无效
- 403：身份有效但没有权限
- 404：隐藏资源是否存在

同一接口对“不存在资源”和“其他租户资源”应尽量保持一致行为。

日志不得输出：

- 完整手机号
- 完整邮箱
- 完整微信号
- 管理员密码
- Session
- Token
- 其他租户的完整业务数据

---

## 18. Migration 规则

修改 Migration 前必须检查已有 Migration 顺序。

禁止：

- 直接修改已经执行过的旧 Migration
- 未授权执行远程 D1 Migration
- 给现有数据错误设置默认租户
- 在无回填方案时直接把字段改成非空
- 删除仍在使用的租户字段
- 通过重建表丢失已有数据
- 关闭外键检查来掩盖错误
- 修改远程生产数据用于测试

Migration 必须验证：

- 全新数据库从零执行全部 Migration
- 已有数据库增量执行最新 Migration
- `PRAGMA foreign_key_check;` 结果为空
- 不存在孤立租户记录
- 不存在空 `tenant_id`
- 正式租户数据保持正确
- 演示租户数据保持正确
- 租户内唯一约束正确
- 没有连接远程 D1

---

## 19. 强制测试矩阵

任何新增或修改租户功能，都至少必须验证：

1. `qianlin-travel` 可以读取自己的数据。
2. `qianlin-travel` 可以在权限允许时修改自己的数据。
3. `qianlin-travel` 不能读取 `yunnan-demo` 的私有数据。
4. `qianlin-travel` 不能修改 `yunnan-demo` 的数据。
5. `qianlin-travel` 不能删除 `yunnan-demo` 的数据。
6. 客户端伪造 `tenantId` 必须失败。
7. 客户端伪造 `tenant_id` 必须失败。
8. 客户端伪造 `tenantSlug` 必须失败。
9. 提交其他租户资源 ID 必须失败。
10. 伪造其他租户 Session 必须失败。
11. 过期 Session 必须失败。
12. 被篡改的 Session 必须失败。
13. 批量操作不能混入其他租户资源。
14. Tenant A 操作后 Tenant B 数据必须保持不变。
15. 错误响应不得泄露 Tenant B 资源是否存在。
16. 日志不得输出 Tenant B 敏感数据。
17. 删除操作不能跨租户级联删除数据。
18. 资源自身 slug 只能在当前租户范围内生效。

不能只测试正常成功路径。

必须包含真实的跨租户失败测试。

---

## 20. 测试要求

涉及租户查询、Schema 或普通租户约束时，应根据当前 `package.json` 运行相关命令。

当前项目主要命令：

```bash
npm run lint
npm run build
npm test
npm run test:integration:local
```

涉及以下内容时，必须运行本地 D1 和 HTTP 集成测试：

- Migration
- 数据写入
- 后台保存
- 咨询提交
- Session
- Cookie
- 跨租户访问
- 数据库约束
- 批量操作
- 管理员权限
- 租户资源关联

不得只创建测试而不执行测试。

不得通过以下方式让测试通过：

- 删除失败测试
- 跳过测试
- 降低断言
- 删除跨租户场景
- 删除认证失败场景
- 用 Mock 完全替代关键数据库测试
- 信任客户端 `tenantId`
- 给查询增加隐藏默认租户
- 修改测试数据掩盖业务错误

---

## 21. 不得自动执行的操作

未经用户明确授权，不得：

- 执行远程 D1 Migration
- 修改生产数据库
- 清空远程数据库
- 删除远程 Migration 记录
- 修改真实域名
- 修改生产环境变量
- 使用真实客户数据测试
- 输出真实咨询信息
- 把 `.env.local` 提交到 GitHub
- 把 `.dev.vars` 提交到 GitHub
- 把生产密钥写入代码或测试
- 把远程数据复制到本地测试数据库

本地集成测试必须使用项目自己的独立本地 D1 状态目录。

---

## 22. 修改前检查

开始租户相关任务前必须确认：

1. 本次功能是否读取或写入租户数据？
2. 可信租户 ID 从哪里获得？
3. 是否存在客户端可控制的租户字段？
4. 涉及哪些租户表？
5. 查询、更新和删除是否都限制租户？
6. 是否涉及批量操作？
7. 是否涉及跨表关联？
8. 是否需要新索引或唯一约束？
9. 是否会影响 `yunnan-demo`？
10. 是否已有跨租户失败测试？
11. 是否涉及 Migration？
12. 是否存在误操作远程 D1 的风险？

---

## 23. 修改后检查

完成修改后必须确认：

1. 是否出现没有租户条件的数据查询？
2. 是否允许客户端修改 `tenant_id`？
3. 是否错误拒绝了合法资源 slug？
4. 是否新增没有外键的租户表？
5. 唯一约束是否错误变成全平台唯一？
6. 是否存在跨租户 JOIN？
7. 是否测试 Tenant A 访问 Tenant B？
8. Tenant B 数据是否保持不变？
9. 是否真正执行相关测试？
10. 是否连接了远程数据库？
11. 是否在日志中输出个人信息？
12. 是否留下未说明的安全风险？

## 25. 与其他 Skill 的配合

涉及租户数据时，必须同时遵守：

- `tenant-isolation`
- `testing-validation`

当仓库中已经存在对应 Skill 时：

- 部署任务同时遵守 `deployment-operations`
- 用户和权限任务同时遵守 `auth-org-rbac`

如果对应 Skill 尚不存在，不得假装已经读取，也不得自行编造其具体规则。

测试规范不能覆盖或降低租户安全要求。
