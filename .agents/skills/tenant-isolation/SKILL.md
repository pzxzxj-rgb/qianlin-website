# 多租户隔离规范

## 1. 目标

确保 qianlin-website 中的不同旅行社数据严格隔离。

任何租户都不能读取、修改、删除或覆盖其他租户的数据。

数据安全和租户隔离优先于开发便利性、代码简短程度和性能优化。

## 2. 当前项目固定事实

当前项目使用：

- Next.js
- Vinext
- TypeScript
- Cloudflare Workers
- Cloudflare D1
- Drizzle ORM

当前正式租户为：

- `qianlin-travel`

当前演示租户为：

- `yunnan-demo`

当前管理员后台只允许管理：

- `qianlin-travel`

在正式设计用户、组织成员关系和 RBAC 之前，不得擅自把当前管理员认证系统改成通用多租户认证系统。

## 3. 什么时候必须使用本 Skill

以下任务必须使用本 Skill：

- 修改 `db/schema.ts`
- 新建或修改 `drizzle/` 下的 Migration
- 修改 `lib/tenancy/`
- 修改公开租户 API
- 修改 `/api/t/[tenantSlug]/` 下的接口
- 修改后台读取或保存数据的 API
- 修改 `lib/admin/` 下的数据访问代码
- 增加联系方式管理
- 增加线路管理
- 增加目的地管理
- 增加咨询记录管理
- 增加管理员账号、组织或权限功能
- 增加新的租户数据表
- 修改任何包含 `tenant_id` 的查询
- 修改批量更新、批量删除或数据导入功能
- 修改租户隔离测试

以下任务通常不需要使用：

- 纯 CSS 修改
- 不读取数据库的静态文案修改
- 不涉及租户数据的图片压缩
- 单纯调整前端间距或字体
- 完全独立于租户的构建工具配置

## 4. 可信租户上下文

### 4.1 公开网站

公开网站的租户必须来自：

- URL 中的 `tenantSlug`
- 服务端根据 slug 查询数据库后得到的租户记录

不得直接相信客户端请求体中的：

- `tenantId`
- `tenant_id`
- `tenantSlug`
- `slug`

客户端提交的租户字段不得直接决定数据写入哪个租户。

### 4.2 管理后台

管理后台的租户必须来自：

- 已验证的 HttpOnly Session
- 服务端验证通过的管理员租户上下文

不得从以下内容直接决定管理员租户：

- 表单字段
- JSON 请求体
- URL 查询参数
- 浏览器 localStorage
- 浏览器 sessionStorage
- 未验证的 Header

### 4.3 Header

即使以后使用 `X-Tenant-ID`，也只能把它作为租户选择信息。

服务端仍然必须验证：

- 当前用户身份有效
- 当前用户属于该租户
- 当前用户拥有执行操作所需的权限

## 5. 数据查询强制规则

所有租户数据查询必须包含可信租户条件。

正确方向：

```ts
where(
  and(
    eq(table.tenantId, trustedTenantId),
    eq(table.id, resourceId),
  ),
)
```

禁止只通过资源 ID 查询租户资源：

```ts
where(eq(table.id, resourceId))
```

以下操作都必须限制租户：

- SELECT
- INSERT
- UPDATE
- DELETE
- COUNT
- EXISTS
- 批量查询
- 批量更新
- 批量删除
- 关联查询
- 导出
- 后台列表
- 后台搜索

不得依赖开发者“记得手动添加 tenant_id”作为唯一安全机制。

应优先通过统一的数据访问函数、租户 Context 或明确的租户参数传递保证隔离。

## 6. 写入与删除规则

新增租户数据时：

- `tenant_id` 必须来自可信服务端上下文
- 不得直接使用客户端提交的 `tenant_id`
- 不得给租户表设置隐藏的默认租户
- `tenant_id` 不得为空

更新租户数据时：

- 必须同时使用资源 ID 和可信 `tenant_id`
- 不得允许客户端修改资源所属的 `tenant_id`
- 不得允许通过提交其他租户资源 ID 修改数据

删除租户数据时：

- 必须同时验证租户和资源
- 必须确认关联数据不会跨租户删除
- 批量删除必须逐项或通过租户限定条件保证边界

## 7. 数据库 Schema 规则

所有租户专属表原则上必须包含：

```text
tenant_id NOT NULL
```

并建立指向 `tenants.id` 的外键。

当前项目优先使用：

```text
ON DELETE RESTRICT
```

防止误删租户时连带删除大量业务数据。

创建租户数据表时必须检查：

- 是否存在 `tenant_id`
- 是否为 `NOT NULL`
- 是否存在外键
- 是否存在必要的联合索引
- 唯一约束是否为租户内唯一
- 状态字段是否有合法值约束
- Migration 是否兼容已有数据

## 8. 唯一约束规则

租户内唯一的数据，必须把 `tenant_id` 放入唯一约束。

正确示例：

```text
UNIQUE (tenant_id, slug)
UNIQUE (tenant_id, code)
UNIQUE (tenant_id, external_id)
```

除非业务明确要求全平台唯一，否则不得只设置：

```text
UNIQUE (slug)
UNIQUE (code)
```

不同旅行社应当可以拥有相同的线路 slug、目的地编码或内部名称。

## 9. 索引规则

不得机械地给所有表只增加：

```text
INDEX (tenant_id, created_at)
```

索引必须根据真实查询设计。

可能的形式包括：

```text
INDEX (tenant_id, status, created_at)
INDEX (tenant_id, status, display_order)
INDEX (tenant_id, slug)
INDEX (tenant_id, available_for_planning, route_order)
```

建立索引前必须检查：

- 查询中的 WHERE 条件
- 排序字段
- 状态过滤
- 是否存在重复索引
- D1 和 SQLite 是否兼容

## 10. 关联查询规则

关联两个租户表时，不得只根据资源 ID 关联。

必须确认：

- 两张表属于同一租户
- 外键关系不能让 Tenant A 的记录关联到 Tenant B
- JOIN 条件或前置查询包含租户边界
- 返回数据中不包含其他租户记录

对客户端提交的关联资源 ID，例如目的地 ID、线路 ID或咨询 ID，必须重新在当前租户范围内验证。

## 11. 管理后台规则

当前后台固定服务 `qianlin-travel`。

在正式建立以下数据模型前，不得擅自开放其他租户后台：

- users
- tenant_memberships
- roles
- permissions

不得仅通过修改 Session 中的 tenant ID，就宣称已经完成多租户后台。

未来开放第二家旅行社后台前，必须先完成：

- 用户身份模型
- 用户与租户成员关系
- 租户角色
- 服务端权限验证
- 跨租户越权测试
- Session 或 Token 租户策略

## 12. API 输入验证

租户写接口必须拒绝未知字段。

特别需要拒绝客户端提交：

- `tenantId`
- `tenant_id`
- `tenantSlug`
- `slug`
- `ownerId`
- `siteStatus`
- `isDemo`
- 其他可能改变资源归属的字段

不得通过简单地忽略危险字段掩盖错误。

高风险字段应返回明确的 400、401、403 或 404，具体状态码遵循当前接口契约。

## 13. 错误信息规则

跨租户访问不得泄露：

- 其他租户资源是否存在
- 其他租户名称
- 其他租户资源 ID
- 其他租户联系人
- 其他租户咨询数据

根据接口安全策略，可以返回：

- 401：身份无效
- 403：身份有效但没有权限
- 404：隐藏其他租户资源是否存在

不得在错误信息或日志中输出完整个人信息。

## 14. 强制测试矩阵

任何新增或修改租户数据功能，都必须至少验证：

1. Tenant A 可以读取自己的数据。
2. Tenant A 可以在权限允许时修改自己的数据。
3. Tenant A 不能读取 Tenant B 的数据。
4. Tenant A 不能修改 Tenant B 的数据。
5. Tenant A 不能删除 Tenant B 的数据。
6. 修改请求体中的 `tenantId` 不会改变目标租户。
7. 提交 Tenant B 的资源 ID 不会绕过隔离。
8. Tenant A 修改后，Tenant B 数据保持不变。
9. 无效、过期或被篡改的 Session 被拒绝。
10. 批量操作不能混入其他租户资源。
11. 数据库外键和唯一约束可以阻止非法数据。
12. 错误响应不会泄露其他租户信息。

不能只编写正向成功测试。

必须包含真实的跨租户失败测试。

## 15. 当前项目测试要求

涉及租户读取规则、Schema 或普通约束时，应运行：

```bash
npm run lint
npm run build
npm test
```

涉及以下内容时，还必须运行本地 D1 和 HTTP 集成测试：

- Migration
- 数据写入
- 管理后台保存
- 咨询提交
- Session
- 跨租户访问
- 数据库约束

命令：

```bash
npm run test:integration:local
```

不得只创建测试文件而不执行测试。

不得通过以下方式让测试通过：

- 删除测试
- 跳过测试
- 降低断言
- 删除越权场景
- 把失败测试改成只检查状态码存在
- 用 Mock 完全替代关键租户数据库测试

## 16. Migration 规则

修改 Migration 前必须检查已有 Migration 顺序。

禁止：

- 直接修改已经在生产执行过的 Migration
- 给现有租户数据错误地设置默认租户
- 在没有数据回填方案时把可空字段直接改为非空
- 未经明确授权执行远程 D1 Migration
- 直接删除仍在使用的租户字段
- 通过重建表丢失其他租户数据

Migration 必须验证：

- 全新数据库从零执行
- 已有数据库增量升级
- 外键检查通过
- 不存在孤立租户记录
- 两个租户的数据都保持正确

## 17. 修改前检查

开始修改前必须回答：

1. 本次功能是否读取或写入租户数据？
2. 可信租户 ID 从哪里获得？
3. 是否存在客户端可控制的租户字段？
4. 涉及哪些租户表？
5. 查询、更新和删除是否都限制租户？
6. 是否涉及批量操作？
7. 是否涉及跨表关联？
8. 是否需要新索引或唯一约束？
9. 现有测试是否覆盖跨租户访问？
10. 是否可能影响 `yunnan-demo`？

## 18. 修改后检查

完成修改后必须检查：

1. 是否出现没有租户条件的数据查询？
2. 是否允许客户端修改 `tenant_id`？
3. 是否新增了没有外键的租户表？
4. 唯一约束是否错误地变成全平台唯一？
5. 是否存在跨租户 JOIN？
6. 是否测试了 Tenant A 访问 Tenant B？
7. 是否真正执行了测试？
8. 是否修改了远程数据库？
9. 是否在日志中输出了个人信息？
10. 是否留下未说明的安全风险？

## 19. 完成报告格式

完成租户相关任务后，必须输出：

```text
租户上下文来源：
涉及的租户表：
修改的文件：
新增或修改的查询：
跨租户保护方式：
数据库约束：
执行的测试命令：
测试结果：
未执行的测试：
剩余风险：
是否执行远程 Migration：否
```

## 20. 例外规则

完全不属于任何租户的全局表可以不包含 `tenant_id`，例如真正的平台级静态字典。

使用全局表必须明确说明：

- 为什么它属于全平台
- 为什么所有租户共享不会造成数据泄露
- 是否允许租户修改
- 是否需要平台管理员权限

无法确认数据是否属于租户时，默认按租户数据处理，不得默认按全局数据处理。

## 21. 规则优先级

出现冲突时，按照以下顺序处理：

1. 租户隔离与数据安全
2. 数据完整性
3. 认证与授权
4. 生产环境安全
5. 测试完整性
6. 架构一致性
7. 开发便利性
8. 性能优化
