# 测试与验证规范

## 1. 目标

确保 qianlin-website 的每次代码修改，都经过与风险相匹配的测试和验证。

测试的目的不是单纯让命令显示通过，而是确认：

- 新功能按照预期运行。
- 原有功能没有被意外破坏。
- 不同旅行社的数据不会发生串租户。
- 未登录用户不能访问管理后台。
- 客户端不能伪造租户身份。
- 数据库 Migration 不会破坏已有数据。
- 本地可以运行的代码具备正式部署条件。
- 测试过程不会访问或破坏生产数据。

测试完整性优先于开发速度和提交速度。

## 2. 当前项目技术与测试体系

当前项目主要使用：

- Next.js
- Vinext
- React
- TypeScript
- Cloudflare Workers
- Cloudflare D1
- Drizzle ORM
- ESLint
- Node.js Test Runner
- Wrangler 本地 D1
- 本地 HTTP 集成测试

当前项目主要验证命令：

- `npm run lint`
- `npm run build`
- `npm test`
- `npm run test:integration:local`

不得擅自引入新的测试框架。

只有当现有测试工具确实无法覆盖需求时，才可以提出引入新工具，并且必须先说明：

- 为什么现有工具不能满足需求。
- 新工具会增加哪些依赖。
- 新工具会影响哪些脚本。
- 是否会影响 Cloudflare 部署。
- 是否有更简单的替代方案。

## 3. 必须使用本 Skill 的场景

以下任务必须使用本 Skill：

- 新增或修改公开 API。
- 新增或修改后台 API。
- 新增或修改管理员页面。
- 修改管理员登录逻辑。
- 修改 Session 或 Cookie。
- 修改租户解析逻辑。
- 修改任何包含 `tenant_id` 的查询。
- 修改咨询提交逻辑。
- 修改 Turnstile 校验。
- 修改防机器人或限流逻辑。
- 修改表单验证规则。
- 修改数据库 Schema。
- 新建或修改 D1 Migration。
- 修改 Drizzle 查询。
- 新增联系方式管理。
- 新增线路管理。
- 新增目的地管理。
- 新增咨询记录管理。
- 新增图片管理。
- 新增用户、组织或权限系统。
- 修复安全问题。
- 修复可能影响多个模块的问题。
- 修改构建配置。
- 修改 Cloudflare 或 Wrangler 配置。
- 修改环境变量读取逻辑。
- 修改部署流程。

以下任务通常只需要基础检查：

- 纯文字修改。
- 纯 CSS 间距调整。
- 不改变行为的颜色修改。
- 替换静态图片。
- 修改 README 文案。
- 修改不影响程序运行的注释。

即使属于低风险任务，也必须确认没有意外修改业务代码。

## 4. 测试级别

### 4.1 静态检查

静态检查主要用于发现：

- 代码语法错误。
- 未使用变量。
- 错误导入。
- 明显的类型问题。
- 不符合项目规范的代码。
- 不正确的 React 使用方式。

命令：

`npm run lint`

### 4.2 构建检查

构建检查主要用于发现：

- TypeScript 编译错误。
- Next.js 或 Vinext 构建错误。
- Server Component 和 Client Component 边界错误。
- 路由错误。
- 文件导入错误。
- 生产构建无法完成。
- 仅在生产模式出现的问题。

命令：

`npm run build`

### 4.3 自动化测试

自动化测试主要用于检查：

- 输入验证函数。
- 数据转换逻辑。
- 图片白名单。
- 行程规划规则。
- 租户查询约束。
- 渲染后的 HTML。
- SEO 和元数据。
- Turnstile 配置规则。
- 页面和接口的源代码约束。

命令：

`npm test`

### 4.4 本地集成测试

本地集成测试主要用于检查：

- D1 Migration。
- 数据库外键。
- 数据库 CHECK 约束。
- 租户数据隔离。
- 管理员登录。
- Session Cookie。
- 后台写操作。
- API 请求。
- 咨询提交。
- 跨租户攻击。
- 完整 HTTP 请求流程。

命令：

`npm run test:integration:local`

本地集成测试必须使用项目自己的本地 D1 状态目录，不得连接远程 D1。

## 5. 修改类型与最低测试要求

### 5.1 纯文案或纯样式修改

最低要求：

- 运行 `npm run lint`。
- 运行 `npm run build`。

如果修改影响以下内容，还必须运行 `npm test`：

- HTML 结构。
- SEO 内容。
- 页面标题。
- Meta 信息。
- 表单标签。
- 无障碍属性。
- 响应式布局相关结构。
- 页面渲染内容。

纯文案或纯样式修改通常不需要运行本地 D1 集成测试。

### 5.2 React 组件或页面修改

最低要求：

- 运行 `npm run lint`。
- 运行 `npm run build`。
- 运行 `npm test`。

还必须检查：

- 页面可以正常渲染。
- 没有明显的 hydration 问题。
- Server Component 和 Client Component 边界正确。
- 按钮可以正常点击。
- 表单可以正常输入。
- 加载状态完整。
- 成功状态完整。
- 失败状态完整。
- 手机端布局没有明显破坏。
- 页面没有意外显示其他租户数据。

### 5.3 API 或业务逻辑修改

最低要求：

- 运行 `npm run lint`。
- 运行 `npm run build`。
- 运行 `npm test`。

涉及以下内容时，还必须运行 `npm run test:integration:local`：

- 数据库读取。
- 数据库写入。
- Session。
- Cookie。
- 管理员后台。
- 咨询提交。
- 租户数据。
- Origin 校验。
- Turnstile。
- 文件或图片路径验证。
- 跨租户访问。

### 5.4 数据库 Schema 或 Migration 修改

必须运行：

- `npm run lint`
- `npm run build`
- `npm test`
- `npm run test:integration:local`

还必须验证：

- 全新数据库可以从零执行全部 Migration。
- 已有数据库可以增量执行最新 Migration。
- 外键检查通过。
- 不存在孤立记录。
- 租户表的 `tenant_id` 不为空。
- 两个租户的数据不会互相覆盖。
- 唯一约束符合租户内唯一规则。
- 索引符合真实查询。
- Migration 没有连接远程 D1。
- 旧数据升级后仍然可用。

### 5.5 管理员认证或 Session 修改

必须运行全部测试命令。

还必须测试：

- 正确用户名和密码。
- 错误用户名。
- 错误密码。
- 空用户名。
- 空密码。
- 未配置管理员环境变量。
- 未登录访问后台页面。
- 未登录调用后台 API。
- Session Cookie 被篡改。
- Session 已过期。
- Session 租户错误。
- Cookie 包含 HttpOnly。
- Cookie 包含正确的 SameSite。
- 生产环境 Cookie 使用 Secure。
- 退出登录后 Cookie 被清除。
- 登录错误不会泄露用户名是否存在。
- 响应中不返回密码、Token 或完整 Session。

### 5.6 多租户功能修改

任何涉及租户数据的任务，必须同时遵守：

- `tenant-isolation`
- `testing-validation`

必须包含真实的跨租户失败测试。

不能只测试正常成功路径。

## 6. 多租户强制测试矩阵

任何涉及租户数据的功能，至少必须测试以下场景：

1. `qianlin-travel` 可以读取自己的数据。
2. `qianlin-travel` 可以在权限允许时修改自己的数据。
3. `qianlin-travel` 不能读取 `yunnan-demo` 的私有数据。
4. `qianlin-travel` 不能修改 `yunnan-demo` 的数据。
5. `qianlin-travel` 不能删除 `yunnan-demo` 的数据。
6. 请求体伪造 `tenantId: "yunnan-demo"` 必须失败。
7. 请求体伪造 `tenant_id` 必须失败。
8. 请求体伪造其他租户资源 ID 必须失败。
9. 伪造其他租户 Session 必须失败。
10. 过期 Session 必须失败。
11. 被篡改的 Session 必须失败。
12. 一次批量操作中混入其他租户资源必须失败。
13. Tenant A 操作成功后，Tenant B 数据必须保持不变。
14. 错误响应不得透露 Tenant B 的资源是否存在。
15. 日志不得输出 Tenant B 的敏感数据。
16. 删除操作不能跨租户级联删除数据。

跨租户失败测试属于强制测试，不得省略。

## 7. API 强制测试

新增或修改 API 时，应根据接口风险测试以下内容。

### 7.1 请求方法

测试：

- 正确 HTTP 方法。
- 不支持的 HTTP 方法。
- 缺少请求体。
- 非 JSON 请求。
- JSON 格式错误。
- 请求体为空。
- 请求体超过大小限制。

### 7.2 输入字段

测试：

- 必填字段缺失。
- 字段类型错误。
- 空字符串。
- 只有空格。
- 超出最大长度。
- 未知字段。
- 危险字段。
- HTML 内容。
- Script 内容。
- 非法 URL。
- 非法枚举值。
- 非法图片路径。
- 路径穿越内容。
- 外部图片地址。
- `data:` 地址。
- `blob:` 地址。

### 7.3 身份与来源

测试：

- 未登录。
- Session 无效。
- Session 过期。
- Session 被篡改。
- Origin 不合法。
- 租户不匹配。
- 权限不足。
- 请求伪造租户字段。
- 请求伪造资源归属字段。

### 7.4 响应结果

检查：

- 成功状态码正确。
- 失败状态码正确。
- `Cache-Control` 符合要求。
- 错误信息不泄露内部实现。
- 错误信息不泄露其他租户资源。
- 响应中不包含密码。
- 响应中不包含 Token。
- 响应中不包含 Session。
- 响应中不包含不应公开的租户字段。
- 写入成功后数据库内容正确。
- 写入失败后数据库内容没有被部分修改。

## 8. 表单测试

新增或修改表单时必须检查：

- 初始值正确。
- 必填项提示正确。
- 字数限制正确。
- 字段类型限制正确。
- 未知字段会被服务端拒绝。
- 提交中按钮不可重复点击。
- 成功提示正确。
- 失败提示正确。
- 网络异常提示正确。
- Session 失效提示正确。
- 服务端仍然执行最终验证。
- 客户端验证不能替代服务端验证。
- 重复提交不会意外创建多条数据。
- 未保存离开提醒符合预期。
- 取消按钮不会意外保存。
- 页面刷新后显示数据库最新内容。

涉及个人信息的表单还必须检查：

- 隐私同意是否必填。
- 日志是否输出个人信息。
- 测试输出是否包含真实手机号。
- 测试输出是否包含真实邮箱。
- 测试数据是否为明确的虚构数据。
- 错误响应是否返回完整个人信息。

## 9. 数据库测试

数据库相关测试必须检查：

- 表是否存在。
- 字段类型是否正确。
- 非空约束是否正确。
- 默认值是否合理。
- 外键是否有效。
- 删除策略是否正确。
- 唯一约束是否正确。
- 租户内唯一是否包含 `tenant_id`。
- 联合索引是否匹配实际查询。
- CHECK 约束是否生效。
- Migration 顺序是否正确。
- 全新安装路径可以运行。
- 已有数据库升级路径可以运行。
- 不存在孤立数据。
- 不存在空租户 ID。
- 不存在错误默认租户。

必须执行数据库外键检查。

SQLite 和 D1 检查命令逻辑应包含：

`PRAGMA foreign_key_check;`

正常结果应为空。

不得为了让测试通过而关闭外键检查。

## 10. 安全回归测试

以下问题修复后必须添加安全回归测试：

- 跨租户漏洞。
- 身份认证绕过。
- Session 伪造。
- Session 过期未失效。
- 非法 Origin 请求。
- XSS 或危险输入。
- 非法图片路径。
- 路径穿越。
- 敏感数据泄露。
- Migration 数据损坏。
- 未登录用户访问后台。
- 未授权用户修改数据。
- 请求体伪造租户字段。
- 请求体过大导致资源问题。

安全问题修复以后，必须保留能够重现旧问题的测试。

不能只修复代码而不留下测试。

## 11. 禁止行为

严禁通过以下方式让测试通过：

- 删除失败测试。
- 注释失败测试。
- 使用 `.skip`。
- 使用 `.only`。
- 降低断言严格程度。
- 把具体断言改成只检查有返回值。
- 删除失败状态码检查。
- 删除跨租户测试。
- 删除认证失败测试。
- 用 Mock 完全代替关键数据库测试。
- 捕获异常但不让测试失败。
- 修改测试数据来掩盖业务错误。
- 因为测试耗时而默认跳过集成测试。
- 未运行测试却声称测试通过。
- 只运行单个测试文件却声称全部测试通过。
- 把真实错误写成已知警告后忽略。
- 为通过测试而放宽安全校验。
- 为通过测试而允许未知字段。
- 为通过测试而信任客户端 `tenantId`。

如果测试本身确实错误，必须先说明：

- 测试为什么错误。
- 原规则为什么不再适用。
- 新的预期行为是什么。
- 修改测试是否存在安全影响。
- 是否需要更新项目文档。

## 12. 不得自动执行的操作

未经用户明确授权，不得：

- 执行远程 D1 Migration。
- 清空远程数据库。
- 修改生产数据。
- 使用真实客户咨询作为测试数据。
- 把 `.env.local` 提交到 GitHub。
- 把 `.dev.vars` 提交到 GitHub。
- 在测试日志中输出管理员密码。
- 把生产密钥写进测试文件。
- 修改真实域名配置。
- 修改生产 Turnstile 密钥。
- 连接生产数据库执行测试。
- 把生产数据复制到测试数据库。
- 删除生产 Migration 记录。

本地集成测试必须使用独立的本地 D1 状态目录。

## 13. 测试失败处理流程

测试失败时必须：

1. 记录失败的命令。
2. 找到第一个有意义的错误。
3. 判断属于代码错误、测试错误还是环境错误。
4. 修复根本原因。
5. 重新运行失败的测试。
6. 修复后重新运行相关完整测试。
7. 确认没有新增其他失败。
8. 报告是否仍有未解决问题。

不得在多个错误之间盲目修改代码。

不得只运行最后失败的测试文件，就宣称整个项目已经通过。

## 14. 修改前检查

开始任务前必须回答：

1. 本次修改属于低风险、中风险还是高风险？
2. 会影响哪些页面？
3. 会影响哪些 API？
4. 会影响哪些数据库表？
5. 是否涉及租户数据？
6. 是否涉及身份认证？
7. 是否涉及个人信息？
8. 是否涉及 Migration？
9. 当前已有哪部分测试？
10. 缺少哪些失败场景？
11. 最低需要运行哪些命令？
12. 是否需要真实 HTTP 测试？
13. 是否需要本地 D1 测试？
14. 是否存在远程数据库误操作风险？

## 15. 修改后检查

完成任务后必须确认：

1. 是否为新逻辑添加测试？
2. 是否包含成功路径？
3. 是否包含失败路径？
4. 是否包含权限测试？
5. 是否包含租户边界测试？
6. 是否运行了要求的全部命令？
7. 是否有测试被跳过？
8. 是否有警告被忽略？
9. 是否为了错误代码修改测试？
10. 是否误用了真实个人数据？
11. 是否访问了远程 D1？
12. 是否修改了生产配置？
13. 是否仍然存在残余风险？
14. 是否需要人工浏览器检查？

## 16. 功能完成标准

功能只有同时满足以下条件才算完成：

- 代码已经保存。
- 静态检查通过。
- 构建通过。
- 相关自动化测试通过。
- 必要的本地集成测试通过。
- 跨租户测试通过。
- 没有测试被跳过。
- 没有连接远程数据库。
- 没有提交真实密钥。
- 没有使用真实客户数据。
- 已明确报告未测试内容。
- 已明确报告剩余风险。

代码已经写完，不等于任务已经完成。

## 18. 低风险例外

纯文案或纯 CSS 修改可以不运行本地 D1 集成测试，但必须同时满足：

- 不改变表单字段。
- 不改变交互行为。
- 不改变 API。
- 不改变租户逻辑。
- 不改变认证逻辑。
- 不改变数据库。
- 不改变环境变量。
- 不改变部署配置。
- 不改变安全校验。

使用低风险例外时，必须在完成报告中说明理由。

无法确定修改是否属于低风险时，默认按照较高风险处理。

## 19. 与其他 Skill 的配合

涉及租户数据时，必须同时遵守：

- `tenant-isolation`
- `testing-validation`

先满足租户隔离规则，再设计测试。

以后涉及部署时，必须同时遵守：

- `deployment-operations`
- `testing-validation`

以后涉及用户和权限时，必须同时遵守：

- `auth-org-rbac`
- `tenant-isolation`
- `testing-validation`

测试规则不能覆盖或降低安全规则。

## 20. 规则优先级

发生冲突时，按照以下顺序处理：

1. 租户隔离与数据安全。
2. 数据完整性。
3. 认证与授权。
4. 个人信息保护。
5. 生产环境安全。
6. 测试真实性。
7. 架构一致性。
8. 开发便利性。
9. 执行速度。
